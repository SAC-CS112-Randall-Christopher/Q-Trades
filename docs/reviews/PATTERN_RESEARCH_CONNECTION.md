# Pattern evidence through the existing researcher

The daily analyzer and immutable comparison preparation are installed from PR83 at
`c653b136f4f0d4fac3f9855bbbb4c40b21a3c8a9`. They retain native scanner findings and
the original preparation/current-input waits. A researcher still needs an explicit
successor contract to use that evidence with the fixed v4 method bank. This source
continuation lives in draft PR75 with its existing archive/recovery owner; it creates
no second scheduler, financial writer or model-serving backend.

## Evidence and execution

An explicitly configured successor selects one supported BTCUSD native5m breakout
or retest from the latest immutable daily shortlist of up to five eligible markets.
It verifies the exact saved finding, source archives, causal recognition and declared
method mapping, and prepares it through the same `PatternComparisons` owner used by
the HTTP workflow. A daily rank is a research priority, not a probability of success.
Other symbols, frames and pattern mechanisms remain unsupported for this fixed
comparison; their recorded evidence remains available without inventing a mapping.

Original detector motivation stays distinct from the fixed v4 breakout-retest versus
cost-breakout hypothesis. The scanner uses confirmed native pivot zones; the bank
uses its own rolling-range retest. The original UUID, issued bundle, finding hash,
coverage and preparation-time evaluation remain immutable. Current execution uses
separate contiguous closed-minute inputs, available book and current eligibility.
It does not turn a partial native window into a full year or ten hours into a
complete 24-hour observation.

Question publication uses the existing registry, unique selection records and
request identity. Repeated ticks, concurrent workers, restart and republication of
the same native event cannot create another question. A timestamp or UUID alone
does not establish new evidence. Existing work waits, dependency recovery, review
timing, daily budgets, used-rule checks, holdouts and unsuccessful answers retain
their authority. A legitimate request for later data can carry the exact original
preparation into the existing dependency-resume path while retaining the separately
observed inputs. An unavailable or adverse answer is not permission for a preferred
answer retry.

Publishing a fresh numerical evaluation rechecks protected intervals and records
its actual matched candle window as exposed evidence in the same registry
transaction. Those newly evaluated candles cannot later be reserved as an unseen
holdout. A lost task lease or failed protection check retains neither a new
evaluation nor an orphan disclosure.

The resulting task uses the existing researcher answer, deterministic numerical
evaluation, shared archive owner, independent reviewer and proposal inbox. Paper
admission, funding, account reservations and maturity/outcome processing remain in
the existing Lab and engine. Selection/preparation alone cannot change an account
or place an order. The recorded outcome, including low information or data blocked,
drives existing followup and teaching; a successful software fixture is not a
successful trading hypothesis.

The v8 followup references the exact frozen comparison and proposal instead of
repeating the earlier preparation controls. Its scored evidence preserves the
original outcome, null economic values, costs, coverage, candidate/reference
execution samples, qualification and dependence disclosures. The complete scored
event stays unchanged in the task and lesson; its identity and hash bind the
model-facing projection. A matched before/after packet check uses the same retained
event and unchanged context guard. This is a packet repair, not a measured runtime
speedup or a trading-capacity result.

## Explicit contract and preserved authority

The successor is `reviewed-rule-role-v8` with explicit
`qtrades-peft-paper-pilot-v5` and `pattern-question-selection-v1`. The older v5/v6/v7
contracts, hashes, original packets and pilot-v1 through v4 grants stay unchanged.
The new contract accepts the actual hyphenated v4 method identifiers and exposes
their active controls. Inactive compatibility fields such as lookback and
volume_multiple are identified as inactive, rather than presented as parameters
that change these fixed rules.

The new grant binds the same model identity and resource profile with an explicit
new contract/hash. No existing grant is upgraded or reinterpreted. Marked tasks
require the exact current selection authority before allowance reservation and
transport dispatch. Activation, financial monitoring, balance, paper freshness,
input eligibility, storage/recording reserves, ownership and model resource limits
remain protected. The real PEFT profile retains its 8,192-token context and
1,024-token output limit. Its existing conservative byte preflight and the native
runner's token guard remain authoritative. A synthetic 9,000-context fixture uses
UTF-8 bytes as a conservative input-token bound, plus output/template reserves. It
checks the compact model-facing summary, which references retained full evidence
instead of transmitting raw archives. That fixture does not
measure actual tokenizer fit, model capacity or coexistence. Those remain a separate
proof stage.

Admission and snapshot validation use fresh observation clocks after the work they
validate, while keeping the numerical causal cutoff separate. The actual final
book/frame frozen after archive work is validated at its capture time; a later
check of another frame does not validate the original snapshot.

## Verification and next operating decision

Focused native fixtures use actual disposable scanner/registry/preparation/worker
owners and software model callbacks. They exercise one atomic publication,
restart/concurrency, protected-input waits, immutable unavailable/adverse outcomes,
old contract pins, matched archived inputs, independent review and existing Lab
admission/outcome routes. Browser fixtures use actual API GETs and compiled UI for
task-to-original-preparation/finding navigation, immutable reload and narrow-screen
layout; no HTTP evidence mocking or actual model inference is involved. Final exact
commands, failures, hashes and hosted checks belong to the PR/issue checkpoint.
The panel offers new manual questions only with an available current compatible
mode; an initial or later status failure preserves original request recovery
without allowing a new request ID.

This source change does not enable the installed daily producer, select a new
operating grant/profile, restart services, fund a new trial, dispatch a model,
consume holdouts, train, promote, download/convert a model or activate external
review. A finite operating test requires separate approval for the reviewed source
installation and explicit v5/v8 profile/grant, bounded native scanner preparation,
and the model/reviewer requests and prospective pair under the unchanged policy.
The test should bind its exact candidate/profile/source, one unused retained task
and finite request/trial allowance, preserve adverse outcomes, and observe paper
freshness, financial balance, recording omissions/resource pressure and the full
after-cost account outcome. It cannot reuse a consumed original attempt or silently
extend its old permission. Any broader supported method/symbol mapping is another
reviewed source proposal.
